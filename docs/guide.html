What is MCP?

The Model Context Protocol (MCP) is an open standard that lets AI assistants — such as Claude — discover and invoke external tools at runtime. Instead of being limited to the knowledge baked into the model, an MCP server exposes a set of tools that the assistant can call to read data, perform actions, or generate artifacts on behalf of the user.

An MCP server is an ordinary program. It is launched by the AI tool, communicates over standard input and output, and advertises the tools it provides. Servers are composable: an agent can call one server to gather information and hand the result to another.

What is pondhawk-generation?

pondhawk-generation renders Liquid templates against a structured input model and writes the result to disk. It exists for artifacts that must all follow the same pattern — a fleet of entities, DTOs, API clients, command handlers, resources — where consistency across the whole set matters more than any individual file.

It knows nothing about databases, or C#, or any particular target. What gets generated is determined entirely by the model you write and the templates you author.

Why a generator at all? Code generation only earns its keep when there is repetition. A one-off class you write by hand. The moment it is worth generating, there is a list driving a loop — and that list is what pondhawk takes as input.

To generate from an existing database, pair pondhawk with a schema-aware MCP server and let the agent feed one from the other. pondhawk does not connect to databases itself.

Registering in Claude Code

Option A — CLI

claude mcp add pondhawk -- pondhawk-generation-mcp --project /path/to/your/project

Option B — Manual JSON config

{
  "mcpServers": {
    "pondhawk": {
      "command": "pondhawk-generation-mcp",
      "args": ["--project", "/path/to/your/project"]
    }
  }
}

The --project argument points at the directory holding pondhawk.project.json. The server reads and writes only inside that directory.

Getting Started

  1. 1
    Scaffold the project. Ask the agent to run init. You get pondhawk.project.json, a starter model.json, two example templates, JSON schemas for editor autocompletion, AGENTS.md, and .env.
  2. 2
    Describe what to generate. Edit model.json so it lists the things you want files for.
  3. 3
    Author the templates. One Default<Kind> macro per kind of node in your model.
  4. 4
    Validate. validate_config catches unparseable templates, unknown filters, overrides that match no node, and templates that would generate nothing.
  5. 5
    Generate. generate renders every template and writes the files. Read one of them before declaring victory.

The Input Model

model.json holds a tree of nodes. Every node has a Name and a Kind, and may have Children. Everything else you write on a node is metadata, and templates read it as an ordinary member — "Type": "int" is reached as {{ p.Type }}, with no Metadata. prefix. 

{
  "$schema": "./model.schema.json",
  "Name": "Catalog",
  "Nodes": [
    {
      "Name": "Product",
      "Kind": "Class",
      "Children": [
        { "Name": "Id",    "Kind": "Property", "Type": "int" },
        { "Name": "Price", "Kind": "Property", "Type": "decimal", "IsNullable": false }
      ]
    }
  ]
}

Nodes nest to any depth. Two levels suit a class with properties; three suit a resource whose operations have parameters.

Kind is yours to choose. It names what a node is, and it selects the macro that renders it. Nothing in the engine has a list of valid kinds.

Templates & Dispatch

Templates are Liquid, rendered by Fluid. Write one Default<Kind> macro per kind, and let {% dispatch %} pick the right one: 

{%- macro DefaultClass(c) %}
public partial class {{ c.Name | pascal_case }}
{%- endmacro %}

{%- macro DefaultProperty(p) %}
    public {{ p.Type | type_nullable: p.IsNullable }} {{ p.Name | pascal_case }} { get; set; }
{%- endmacro %}

{% dispatch item %}
{
{%- for p in item.Children %}
{% dispatch p %}
{%- endfor %}
}

This is the consistency guarantee: every node of a kind goes through one macro, so changing that macro changes every artifact at once.

Variants

When one node needs to render differently, define a <Variant><Kind> macro and point an override at it. Dispatch falls back to Default<Kind> when the variant macro is missing, so an override naming a macro you have not written yet degrades rather than breaking. 

{%- macro CurrencyProperty(p) %}
    [Column(TypeName = "decimal(18,2)")]
    public decimal {{ p.Name | pascal_case }} { get; set; }
{%- endmacro %}

Overrides

Overrides address nodes by path and change how they render for one artifact — selecting a variant macro, merging extra metadata, or dropping the node entirely. 

"Overrides": [
  { "Path": "Product/Price", "Artifact": "entity", "Variant": "Currency" },
  { "Path": "*/CreatedAt",   "Artifact": "entity", "Ignore": true },
  { "Path": "Order/**",      "Artifact": "dto",    "Metadata": { "Access": "internal" } }
]
FieldMeaning
PathSlash-delimited node path. * matches one node, ** matches any depth.
ArtifactTemplate key. Required with Variant; omit to apply to every template.
VariantMacro variant to render matched nodes with.
IgnoreDrops matched nodes from that artifact.
MetadataMerged onto matched nodes, overwriting what the model declared.
When several overrides match one node, the one with the most literal path segments wins. Ties go to whichever is listed later — so state the broad rule first and narrow it afterwards.

Configuration Reference

{
  "$schema": "./pondhawk.project.schema.json",
  "OutputDir": "src/Generated",
  "Templates": {
    "entity": {
      "Path": "templates/entity.generated.liquid",
      "OutputPattern": "{{ item.Name | pascal_case }}.generated.cs",
      "Scope": "PerItem",
      "Mode": "Always",
      "AppliesTo": "Class"
    },
    "entity-stub": {
      "Path": "templates/entity.stub.liquid",
      "OutputPattern": "{{ item.Name | pascal_case }}.cs",
      "Scope": "PerItem",
      "Mode": "SkipExisting",
      "AppliesTo": "Class"
    }
  },
  "Values": { "Namespace": "MyApp.Data" },
  "Overrides": [],
  "Logging": { "Enabled": false }
}
FieldMeaning
OutputDirRoot directory for generated files, relative to the project.
TemplatesTemplates to render, keyed by artifact name. The key is what overrides target.
ScopePerItem renders one file per matching node; Single renders one file for all.
ModeAlways overwrites every run; SkipExisting writes once and then leaves it alone.
AppliesToRestricts a template to top-level nodes of one Kind. Omit or use All for every node.
ValuesAnything templates need, read as {{ values.X }}.
LoggingOff by default. Enable to write a rolling log under .pondhawk/logs.

The two-file pattern

Pair an Always template with a SkipExisting one to keep generated code and hand-written code apart. The generated file is overwritten freely; the stub is created once and is then yours. In C# these are partial class halves; other languages have their own equivalents.

Environment Variables

String entries under Values support ${VAR} substitution, resolved from a .env file in the project directory or from the process environment. Use it for anything a template needs but that should not be committed. 

# .env — keep this out of version control
BUILD_STAMP=2026.08.29
LICENCE_KEY=xxxxxxxx
"Values": {
  "Stamp": "${BUILD_STAMP}"
}

validate_config warns about ${VAR} references that resolve to nothing, rather than silently generating files with an empty value in them.

Tips

Read a generated file before declaring success. A template that renders empty is skipped silently, and an unknown metadata key renders as nothing rather than failing. Both look like success in the tool output.
Run validate_config after editing the model. It catches the two mistakes that otherwise produce no files and no error: an override whose path matches no node, and a template whose AppliesTo matches no Kind in the model.
Commit templates and the model. They are project assets, like source. The generated output can be committed or regenerated, whichever suits your build.
Let the agent maintain the templates. They are the highest-leverage part of the project — one macro decides how every artifact of a kind looks.
